# 通用云效项目生命周期 Agent Skill 设计

## 目标

创建符合 [Agent Skills 规范](https://agentskills.io/specification) 的可移植 Skill `yunxiao-project-lifecycle`，通过云效官方 MCP 管理单个本地项目对应的云效项目。Skill 负责依赖预检、项目绑定、动态发现、生命周期操作、风险控制和结果验证；它不绑定任何具体智能体，不保存凭据，不实现第二套云效 API 客户端，也不承担定时调度。

## 架构边界

系统分为四层：

1. **云效 MCP**：提供组织、项目、人员、工作项、迭代和版本的实时读写工具。
2. **通用 Agent Skill**：定义依赖预检、上下文解析、操作流程、安全边界、错误语义和验证规则。
3. **项目绑定文件**：作为智能体无关的仓库级契约，在本地项目中保存其唯一对应的云效组织、项目和经过校验的默认映射。
4. **Automation**：后续负责定时触发。Automation 的写权限独立配置，不继承交互式会话的写权限。

首版要求 MCP 提供组织管理和项目管理等价能力。工具名称、安装目录和客户端配置格式不是核心契约；运行时必须先探测实际能力。不得绕过 MCP 实现另一套业务 API，也不得在能力缺失时静默切换实现。

## Skill 文件结构

```text
huhengbo/skills/
└── skills/
    └── yunxiao-project-lifecycle/
        ├── SKILL.md
        ├── scripts/
        │   ├── doctor.mjs
        │   ├── install.mjs
        │   └── lib/
        │       ├── binding.mjs
        │       └── doctor-core.mjs
        ├── tests/
        │   ├── binding.test.mjs
        │   ├── doctor.test.mjs
        │   └── install.test.mjs
        └── references/
            ├── lifecycle-policy.md
            ├── mcp-setup.md
            └── project-binding.md
```

`SKILL.md` 只使用 Agent Skills 规范要求的 `name` 和 `description` frontmatter，并保留触发范围、主流程和强制不变式。项目绑定、MCP 接入和动作策略分别按需加载，避免复制完整工具文档或静态状态枚举。核心目录不得包含特定智能体的展示元数据或配置文件。

## 规范源与发布位置

唯一规范源为公开仓库 [huhengbo/skills](https://github.com/huhengbo/skills) 的 `skills/yunxiao-project-lifecycle/` 目录，默认分支为 `main`。本机各智能体的安装目录只是该规范源的副本或链接，不得在本地安装目录直接维护分叉版本。

实现时遵循仓库现有 `skills/<skill-name>/` 布局，但新 Skill 不创建客户端专属元数据目录，也不要求加入现有的客户端市场清单。为保持仓库说明与实际定位一致，应将 README 中“Codex Skills”改为“Agent Skills”，并把客户端专属元数据标记为可选适配层；不得删除或改写现有 Skill 的适配文件。

设计文档在实施时保存为 `docs/superpowers/specs/2026-07-15-yunxiao-project-lifecycle-design.md`，与 Skill 一起进入评审分支。实现、验证、README 调整和设计文档应形成一个聚焦提交，通过分支和拉取请求合入 `main`，不直接覆盖默认分支。

## 可移植性与安装边界

Agent Skills 规范定义 Skill 内容格式，但不定义客户端如何发现、安装或配置 MCP。因此分为两个入口：

1. **首次安装入口**：Skill 安装器、Git 仓库下载或人工复制负责从 `huhengbo/skills` 取得核心目录；`scripts/install.mjs` 可将它安装到调用方明确提供的 Skill 搜索路径。未安装的 Skill 无法主动检查或安装自己，这一限制必须明确说明。
2. **运行时入口**：Skill 被加载后先检查云效 MCP 能力；缺失时进入配置引导，禁止继续执行任何云效写操作。

核心包不假设任何客户端目录。安装器或当前智能体负责提供目标 Skill 搜索路径；核心协议不定义默认安装位置。

`scripts/install.mjs` 使用 Node.js 18+，默认 dry-run。它只接受显式 `--target` 或 `AGENT_SKILLS_DIR`，展示源目录、目标目录和计划变更；只有显式 `--apply` 才执行原子复制并保留旧版本备份。它不探测具体客户端、不写 MCP 配置、不保存 Token。没有明确目标路径时返回 `SKILL_INSTALL_TARGET_REQUIRED`，不得猜测。

## MCP 预检与配置引导

每次首次使用以及依赖异常时执行以下状态机：

1. **平台探测**：识别 Windows、macOS 或 Linux、CPU 架构、可用 shell、Node.js 和网络代理环境。
2. **客户端能力探测**：确认当前智能体是否支持远程 Streamable HTTP MCP、自定义 Bearer Token 或环境变量引用。不得通过产品名称猜测配置格式。
3. **MCP 能力探测**：检查是否存在云效组织、项目、成员、工作项、迭代和版本的等价工具。
4. **凭据探测**：只检查 `YUNXIAO_ACCESS_TOKEN` 是否存在，不读取到输出、不记录值、不显示摘要。
5. **Endpoint 探测**：仅允许 HTTPS 云效官方托管地址；检查 DNS、TLS、代理和协议响应，不允许关闭证书验证。
6. **只读认证验证**：调用当前用户或等价只读工具，区分未配置、未认证、无权限、限流、网络失败和工具缺失。
7. **配置引导**：如果客户端支持可验证的 MCP 安装命令或配置接口，先展示目标和变更再协助执行；否则给出适配当前平台的最小手工步骤。不得猜测配置文件路径或格式。
8. **重新加载**：明确提示是否需要新进程或完全重启客户端；不得自动杀死 GUI 进程或重启操作系统。
9. **新会话验证**：重新执行能力探测和只读认证验证，只有全部通过才进入 `READY`。

状态输出统一为 `READY`、`BINDING_MISSING`、`BINDING_INVALID`、`SKILL_INSTALL_TARGET_REQUIRED`、`SKILL_INVALID`、`MCP_MISSING`、`TOKEN_MISSING`、`TOKEN_INVALID`、`AUTH_FAILED`、`PERMISSION_DENIED`、`ENDPOINT_INVALID`、`RATE_LIMITED`、`NETWORK_ERROR`、`UNSUPPORTED_PLATFORM`、`UNSUPPORTED_CLIENT`、`RESTART_REQUIRED`、`CONFIG_ERROR` 或 `CAPABILITY_MISSING`。任何非 `READY` 状态都禁止云效写操作；`BINDING_MISSING` 只允许组织和项目发现等只读操作。

### 通用诊断脚本

`scripts/doctor.mjs` 使用 Node.js 18+，只承担跨平台、客户端无关的只读诊断：

- 识别 `win32`、`darwin`、`linux` 和架构。
- 检查 Token 是否存在但绝不输出值。
- 校验官方 Endpoint、DNS、TLS、HTTP/MCP 响应和只读认证。
- 检查仓库根目录的 `yunxiao.toml` 是否可解析；绑定存在时通过 `get_project` 只读调用核对项目 ID、名称和编码快照。本地格式合法不等于写入就绪。
- 以人类可读或 JSON 形式输出状态和安全的修复建议；只有远端绑定核验成功时才输出 `writeReady: true`。

脚本默认只读，不修改客户端配置、shell profile、系统代理、证书或仓库。客户端配置由当前智能体按其官方能力完成；缺少 Node.js 时明确报告并执行文档化的人工预检，不伪装成功。

### 凭据原则

- 统一使用环境变量名 `YUNXIAO_ACCESS_TOKEN`，Token 不进入仓库、Skill、命令参数、URL、日志或聊天。
- 引导用户在本机安全输入 Token；不得要求用户粘贴到对话中。
- GUI 客户端可能无法继承启动后的 shell 环境变量，必须通过新进程验证，不能仅检查配置文件后宣称成功。
- 若客户端不支持环境变量引用或安全凭据存储，停止自动配置并说明风险；未经用户明确同意不得把 Token 写入明文配置。
- 中心站默认使用 `https://openapi-rdc.aliyuncs.com/ai/mcp`，仅按官方规则支持专有 Region，不接受任意用户提供的 HTTP Endpoint。

## 项目绑定规范

### 文件位置

每个本地项目使用一个绑定文件：

```text
<project-root>/yunxiao.toml
```

优先将最近的 Git 仓库根目录作为项目根目录；没有 Git 仓库时，使用当前智能体工作区根目录。只读取该根目录下的 `yunxiao.toml`。进入嵌套 Git 仓库后不得继承外层仓库的绑定。首版不支持一个本地项目绑定多个云效项目；这类场景必须拆分配置方案后再扩展。

绑定格式不依赖任何智能体。兼容 Agent Skills 的客户端、CI 任务和后续同步服务都应读取同一份 `yunxiao.toml`，不得各自维护平行的项目映射。

### 文件格式

```toml
schema_version = 1

[organization]
id = "<organization-id>"
name = "组织显示名称"

[project]
id = "<project-id>"
name = "聚浪智能体"
custom_code = "XJLAI"

[workitem_types.requirement]
id = "<requirement-type-id>"
name = "需求"

[workitem_types.bug]
id = "<bug-type-id>"
name = "缺陷"

[assignees.requirement]
user_id = "<product-owner-user-id>"
name = "产品负责人"

[assignees.bug]
user_id = "<bug-owner-user-id>"
name = "缺陷负责人"
```

字段规则：

- `schema_version`、`organization.id` 和 `project.id` 为必填项。
- `organization.name`、`project.name` 和 `project.custom_code` 是供人核验的快照，不作为远程写入目标。
- `workitem_types.requirement`、`workitem_types.bug` 和 `workitem_types.task` 是可选的默认工作项类型映射。存在时同时保存稳定 ID 和显示名称。
- `assignees.requirement`、`assignees.bug` 和 `assignees.task` 是可选的默认负责人映射。存在时同时保存稳定用户 ID 和显示名称。
- 用户在当前请求中明确指定的类型或负责人优先于默认映射。没有默认映射且动态查询得到多个候选时，必须请求用户选择。
- Token、AccessKey、Cookie、MCP 地址及其他凭据禁止写入绑定文件。
- 状态 ID、迭代 ID 和版本 ID 不写入首版绑定文件，必须根据当前工作流和实时数据动态获取。
- 文件可以纳入版本控制以便团队共享；如果组织或项目标识属于内部敏感元数据，由项目自行加入 `.gitignore`。Skill 不自动决定是否提交。

### 绑定解析与校验

执行任何云效写操作前必须：

1. 找到唯一的项目根目录和绑定文件。
2. 解析 TOML，拒绝未知的 `schema_version`、缺失字段或重复定义。
3. 用 `organization.id` 和 `project.id` 调用 MCP 读取远程项目详情。
4. 断言请求使用的组织 ID 和返回的项目 ID 与文件一致。
5. 对比显示名称和项目编码。若远程名称或编码变化，阻断写入并提示用户确认更新绑定文件。
6. 使用默认工作项类型前，校验它仍属于该项目且类别匹配；使用默认负责人前，校验成员仍属于该组织、处于可用状态并可被分配。

没有绑定文件时，只能执行组织和项目发现等只读操作。不得按名称、最近访问记录或当前组织猜测写入目标。用户明确选择项目并要求绑定后，才能创建绑定文件。

## 生命周期主流程

所有单条操作遵循同一顺序：

1. **解析上下文**：读取并验证项目绑定。
2. **解析目标**：优先验证用户明确指定的目标，其次验证项目默认映射，否则动态查询工作项类型、人员、工作流、迭代或版本；名称匹配必须得到唯一稳定 ID。
3. **读取现状**：读取目标项目或工作项的最新状态。
4. **校验意图**：确认用户明确要求写入，并检查字段、当前状态、目标状态和重复候选。
5. **执行一次**：调用唯一的 MCP 写工具，不并行提交同一逻辑变更。
6. **回读验证**：读取同一资源，逐项核对项目 ID、对象 ID 和请求修改的字段。
7. **报告结果**：区分已验证成功、已提交但未验证、拒绝执行和失败。

## 动作策略

| 动作 | 首版策略 |
|---|---|
| 查询项目、需求、缺陷、人员、迭代、版本、评论和活动 | 直接执行 |
| 创建单条需求或缺陷 | 用户明确要求、绑定有效、类型唯一且完成重复检查后直接执行 |
| 更新单条标题、描述、优先级、负责人、参与人、迭代或版本 | 目标唯一、字段合法且写前读取最新状态后直接执行 |
| 添加单条评论 | 目标唯一且内容明确时直接执行 |
| 单条状态流转 | 当前状态和目标状态明确，且动态工作流允许时直接执行 |
| 同名项目、同名人员、同名迭代或重复工作项候选 | 阻断并请求用户选择 |
| 删除、批量创建或批量修改 | 首版禁止调用写工具 |
| 真正归档 | 官方 MCP 未暴露明确归档工具时报告不支持，不以删除或完成状态代替 |
| 定时任务中的写操作 | 首版禁止；后续由 Automation 单独定义授权范围 |

“直接执行”只适用于用户明确表达的单条写入意图。分析、总结、检查、规划或询问能力不构成隐含写入授权。

## 重复提交与并发

官方 MCP 当前没有在相关工具模式中暴露统一的幂等键或版本条件写入，因此 Skill 不得承诺严格的服务端幂等或乐观锁。

- 创建前按项目、工作项类别和精确标题搜索活跃工作项。发现可能重复项时停止创建并展示候选。
- 写调用超时或返回不确定结果时，先通过目标查询、评论列表或活动记录判断副作用是否已发生；不得立即重试。
- 评论重试前检查最新评论是否已经存在相同内容。
- 写前读取和写后回读之间发现目标状态变化时，报告冲突，不覆盖、不自动补偿。
- MCP 将来暴露版本号、ETag 或幂等参数时，再在后续 schema 版本中加入条件写入。

## 结果和错误语义

每个写操作必须给出以下结果之一：

- **已验证成功**：回读对象和请求字段一致。
- **已提交但未验证**：写请求可能成功，但回读失败或最终状态尚未一致。不得自动重试。
- **已拒绝**：绑定、目标、权限、工作流、重复检查或动作策略不满足。
- **失败**：MCP 明确返回失败，且没有已发生副作用的证据。

错误报告包括阶段、对象 ID、参数摘要、是否可能产生副作用和安全的下一步。不得输出 Token、认证头或不必要的个人信息；不得吞掉 MCP 原始错误含义。

## 审计边界

首版使用云效工作项活动、评论记录和操作后的结构化结果作为审计依据。Skill 不具备独立、不可篡改的持久化审计能力，不得声称已经提供此类保证。后续定时自动化若允许写入，应增加独立运行记录、请求标识和失败队列。

## 首版非目标

- 不实现跨项目批量操作。
- 不支持一个本地项目绑定多个云效项目。
- 不创建、删除或归档云效项目。
- 不实现工作项的真正归档替代方案。
- 不实现定时调度、后台服务、数据库或第二套 API 客户端。
- 不把动态云效状态、人员和类型缓存为第二个真相来源。
- 不承诺为未知客户端自动发现或修改私有配置格式。
- 不修改系统代理、证书、shell 启动文件或 GUI 进程环境。
- 不解决未安装 Skill 时的远程分发问题；首次安装由独立安装入口负责。

## 验证设计

### 静态验证

- 使用 Agent Skills 参考实现 `uvx --from skills-ref agentskills validate <skill-dir>` 验证目录、名称和 YAML frontmatter；当前智能体的验证器只能作为附加检查。
- 检查核心目录不包含任何客户端专属安装路径、展示元数据或配置文件。
- 扫描 Skill 文件，确保不存在 Token、当前账户信息或来自真实环境的组织、项目和人员 ID；格式示例只能使用明显占位符。
- 扫描占位符、重复规则、矛盾策略和未引用的文件。
- 对 `doctor.mjs` 和 `install.mjs` 运行格式、类型和 Node.js 18+ 执行检查，并验证所有输出都经过凭据脱敏。
- 验证 `install.mjs` 未提供目标时拒绝安装、默认 dry-run、显式应用时原子复制、已有目录备份以及路径穿越防护。

### 跨平台诊断验证

至少覆盖以下平台分支：

- Windows：PowerShell、命令行启动和 GUI 启动环境。
- macOS：zsh、终端启动和 GUI 启动环境。
- Linux：POSIX shell、终端、用户服务和 CI 环境。

每个平台验证 Token 未设置、Token 无效、权限不足、DNS/TLS/代理失败、404、429、5xx、超时、缺失远程 MCP 能力、配置后需要重启和新进程验证。无法在真实平台执行的分支必须通过注入平台参数的自动化测试覆盖，并明确标记尚未完成真实系统验证。

### 前向场景验证

在不写入线上数据的前提下，用独立代理验证下列工具调用计划：

1. 已绑定项目中创建一条需求。
2. 未绑定时请求创建缺陷，必须零次写调用。
3. 多个同名项目或人员，必须零次写调用。
4. 精确标题存在活跃工作项，必须停止重复创建。
5. 非法状态流转，必须零次状态写调用。
6. MCP 写入超时，必须先回读且不得盲目重试。
7. 写后字段不一致，必须报告“已提交但未验证”。
8. 请求批量修改、删除或归档，首版必须零次写调用。

验证以预期的工具调用序列和写调用次数为判断依据，不只检查自然语言回答。

## 验收标准

- 与云效相关的生命周期请求能够触发 Skill。
